# Развёртывание

## Что здесь проверено, а что нет

| Путь | Состояние |
|---|---|
| `scripts/dev_db.sh` — локальный PostgreSQL без Docker | **Проверен**: полный цикл start/status/stop/повторный start, 16 интеграционных тестов против созданной им базы |
| `Dockerfile` | **Набор файлов проверен, сборка образа — нет**: демона Docker в среде не было. Те же файлы, что копирует образ, собраны в отдельном каталоге, установлены зависимости и запущен процесс под `NODE_ENV=production` и ролью `app_runtime`; `/health` и `/health/ready` ответили. Так нашлась настоящая ошибка наброска — см. ниже |
| `compose.yaml` | **Не проверен**: синтаксис YAML разобран, запуск не выполнялся |

Непроверенные файлы помечены и в самих файлах. Перед первым использованием их нужно запустить и исправить найденное — считать их рабочими нельзя.

Что нашлось при первой же проверке набора файлов: образ копировал только
`services` и не копировал `packages`. Схема конверта команды и закрытые схемы
нагрузки читаются оттуда при загрузке модулей, поэтому контейнер падал бы на
старте с ENOENT — до первого запроса и без внятного сообщения. Проверено
отрицательным контролем: без каталога `packages` процесс не стартует.

Вторая правка — `HOST=0.0.0.0` в образе. По умолчанию сервер слушает петлю, и в
контейнере такой порт снаружи недоступен: проверка готовности не проходит, а в
логе при этом ни одной ошибки.

## Роли базы данных: migration owner, API runtime, worker

Миграции выполняются владельцем таблиц, приложение — отдельной ролью `app_runtime` без `SUPERUSER` и `BYPASSRLS`. Это не формальность: под владельцем политики RLS не действуют, и изоляция пользователей исчезает без единой ошибки. Запуск в production под небезопасной ролью отклоняется проверкой при старте.

Роль создаётся вне миграций — в managed PostgreSQL у мигратора может не быть права создавать роли. `scripts/dev_db.sh` создаёт её для разработки; на сервере роль создаётся один раз вручную:

```sql
CREATE ROLE app_runtime LOGIN PASSWORD 'из secret manager' NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE;
CREATE ROLE app_worker  LOGIN PASSWORD 'из secret manager' NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE;
```

Ролей две. API видит только строки своего пользователя; worker обрабатывает задания всех пользователей, и его расширенный доступ задан отдельными политиками на `jobs` и `outbox_events`, а не отключением RLS для этих таблиц: исключение видно в списке политик, а не спрятано в отсутствии защиты.

Если роли нет, миграция останавливается с явным сообщением.

## Разработка без Docker

```bash
scripts/dev_db.sh start                  # поднимает кластер и роль, печатает обе строки подключения
export DATABASE_URL=postgres://system@127.0.0.1:5433/system_test
npm run test:integration
npm run migrate
npm run dev                      # API
npm run worker                   # фоновая обработка, роль app_worker
scripts/dev_db.sh stop
```

Кластер слушает только localhost и использует доверительную аутентификацию: он одноразовый и не предназначен для реальных данных.

Каталог кластера зависит от того, кто запускает скрипт. Под обычным пользователем это `.pgdata` в репозитории; под root — `/var/lib/postgresql/system-dev`, потому что PostgreSQL работает от пользователя `postgres`, а каталог внутри `/root` ему недоступен на обход. Свой путь задаётся переменной `PGDATA`.

## Разработка через Docker

```bash
cp ops/env.example .env                  # задать POSTGRES_PASSWORD
docker compose -f ops/compose.yaml up --build
```

Процесс `src/worker.ts` уже реализован. Worker отдельным сервисом в Compose ещё не описан; до Telegram deployment добавить/проверить его запуск и отдельный WORKER_DATABASE_URL. Lease correctness требует T-00b, реальные reminder handlers пока отсутствуют.

## Чего здесь нет

Личный пилот и публичная beta (docs/09, раздел 7) требуют TLS reverse proxy, резервных копий с проверенным восстановлением, secret manager и мониторинга. Ничего из этого не настроено и не выбрано: хостинг, регион и бюджет — решение владельца проекта, а не предположение этих файлов.

## Railway: первое развёртывание

Проект `ai-assistant-system`, окружение `production`. Два сервиса: `Postgres`
(образ `postgres-ssl:18`, том 5 ГБ) и `api` (сборка из `ops/Dockerfile`,
ветка `main` репозитория).

Порядок важен: роли создаются **до** миграций, иначе миграция останавливается —
ей некому выдавать права.

### 1. Роли

Managed PostgreSQL не даёт мигратору создавать роли автоматически, поэтому они
заводятся один раз вручную. Строка подключения владельца собирается из
переменных сервиса `Postgres` в панели Railway (`PGPASSWORD`) и адреса TCP-прокси
(`RAILWAY_TCP_PROXY_DOMAIN`, `RAILWAY_TCP_PROXY_PORT`).

```sql
CREATE ROLE app_runtime LOGIN PASSWORD 'свой пароль' NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE;
CREATE ROLE app_worker  LOGIN PASSWORD 'свой пароль' NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE;
```

Пароли придумываются здесь же и больше нигде не хранятся, кроме переменных
Railway. В репозиторий они не попадают.

### 2. Миграции

Выполняются владельцем таблиц, не ролью приложения:

```bash
DATABASE_URL='postgres://postgres:ПАРОЛЬ@ПРОКСИ:ПОРТ/railway' npm run migrate
```

### 3. Переменные сервиса `api`

Заданы заранее: `RAILWAY_DOCKERFILE_PATH`, `NODE_ENV`, `HOST`, `PORT`,
`DEV_AUTH_ENABLED=false`, `TELEGRAM_ALLOWED_USER_IDS`, сроки проверки подписи и
`DATABASE_URL` со ссылкой на пароль роли приложения.

Вручную в панели добавляются два секрета:

| Переменная | Что это |
|---|---|
| `APP_RUNTIME_PASSWORD` | Пароль роли `app_runtime` из шага 1 |
| `TELEGRAM_BOT_TOKEN` | Токен бота от BotFather |

`DATABASE_URL` собран как
`postgres://app_runtime:${{APP_RUNTIME_PASSWORD}}@${{Postgres.RAILWAY_PRIVATE_DOMAIN}}:5432/${{Postgres.PGDATABASE}}`:
приложение ходит в базу по внутренней сети Railway и под ролью без
`SUPERUSER`/`BYPASSRLS`. Под владельцем таблиц политики изоляции не действуют, и
запуск в production с такой ролью отклоняется проверкой на старте — это не
перестраховка, а единственное, что отделяет «изоляция работает» от «изоляция
молча отсутствует».

### Что уже проверено живым запуском

- Сборка образа по `ops/Dockerfile` проходит на Railway целиком, включая
  копирование `packages` — того самого каталога, которого не хватало в первом
  наброске.
- Редактированная запись ошибок работает и в production: неудачный старт дал
  строку `{"event":"api_start_failed","error_name":...,"fingerprint":...}` —
  без строки подключения и без пароля.
- Там же нашлась недоработка самой записи: собственные классы ошибок не задают
  `name`, и в логе оказывалось безликое `Error`. Исправлено — теперь берётся имя
  класса.


## Резервные копии

Railway отдаёт копии тома только на тарифе Pro, поэтому копии делаются сами —
скриптами `ops/backup_db.sh` и `ops/verify_restore.sh`.

Копия ложится **не на ту машину, где база**: дамп снимается с Railway на
собственный сервер. Копия рядом с базой от потери диска не спасает, а
одновременная потеря сервера и Railway маловероятна.

### Снять копию

```bash
export DATABASE_URL='postgres://postgres:ПАРОЛЬ@ПРОКСИ:ПОРТ/railway'
ops/backup_db.sh
```

Каталог по умолчанию — `~/backups/ai-assistant`, хранится 14 дней
(`BACKUP_DIR`, `KEEP_DAYS`). Права: каталог `700`, файлы `600` — в дампе лежат
все личные данные.

Дамп пишется во временный файл и получает имя только после успешной проверки
`pg_restore --list`. Прерванный или обрезанный дамп не должен выглядеть готовой
копией: на такую копию надеются.

### Проверить восстановлением

```bash
ops/verify_restore.sh
```

Восстанавливает самую свежую копию во временную базу локального кластера и
сравнивает число строк с рабочей базой. Временная база удаляется в любом
случае, рабочая не затрагивается.

**Это обязательная часть, а не необязательная.** Копия, из которой ни разу не
восстанавливали, копией не является: о том, что дамп негоден, узнают в тот
единственный день, когда он нужен.

### Ежедневно

```bash
crontab -e
```

```
0 4 * * * cd /root/projects/AI-Assistant-for-Human-Development && DATABASE_URL='postgres://postgres:ПАРОЛЬ@ПРОКСИ:ПОРТ/railway' ops/backup_db.sh >> ~/backups/backup.log 2>&1
0 5 * * 0 cd /root/projects/AI-Assistant-for-Human-Development && DATABASE_URL='postgres://postgres:ПАРОЛЬ@ПРОКСИ:ПОРТ/railway' ops/verify_restore.sh >> ~/backups/restore.log 2>&1
```

Копия ежедневно, проверка восстановлением раз в неделю. Оба скрипта возвращают
ненулевой код при неудаче, поэтому `cron` пришлёт письмо, а мониторинг увидит
сбой.

### Известное ограничение еженедельной проверки

`verify_restore.sh` восстанавливает копию в локальный кластер PostgreSQL. Тот
кластер поднимается вручную (`scripts/dev_db.sh start`) и после перезагрузки
сервера сам не стартует: воскресная проверка тогда упадёт, а увидеть это можно
только в `~/backups/restore.log`.

Ежедневная копия от этого не зависит — она снимается прямо с Railway.

Проверить, что проверка живёт:

```bash
tail -20 ~/backups/restore.log
```

Последняя строка должна быть «Восстановление прошло». Если там ошибка
подключения — поднять кластер и запустить проверку руками:

```bash
bash scripts/dev_db.sh start
. ~/backups/railway.env && ops/verify_restore.sh
```

Правильное решение — автозапуск кластера при загрузке (systemd unit); пока не
сделано и записано как долг.

### Что проверено

Оба скрипта проверены на живой базе, а не прочитаны глазами:

| Случай | Итог |
|---|---|
| Копия базы с данными и восстановление | Схема и строки совпали, код возврата 0 |
| Обрезанный дамп | Восстановление отклонено, код возврата 1 |
| Пустой файл | Отклонён, код возврата 1 |
| Несуществующий файл | Отказ, код возврата 1 |
| Копия без `DATABASE_URL` | Отказ, код возврата 1 |

### Чего эти скрипты не делают

Копии лежат на одном сервере. Его потеря вместе с Railway маловероятна, но
возможна: выгрузка на третье место (объектное хранилище) не настроена.

Восстановление в **рабочую** базу намеренно не заскриптовано. Такая команда
затирает боевые данные, и запускать её нужно осознанно и руками:

```bash
pg_restore --no-owner --no-privileges --clean --if-exists \
  -d 'postgres://postgres:ПАРОЛЬ@ПРОКСИ:ПОРТ/railway' КОПИЯ.dump
```

Роли `app_runtime` и `app_worker` восстановление не создаёт — дамп снят с
`--no-owner --no-privileges`. После восстановления в новый кластер роли
создаются заново по разделу выше, иначе приложение не запустится.
