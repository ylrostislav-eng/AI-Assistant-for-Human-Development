### Проверки сессий на реальной схеме (P1-02, частично)

- Решён вопрос «как прочитать сессию до того, как известен пользователь». Выбрана политика по предъявленному хешу (`sessions_lookup_by_hash`, миграция 006): вызывающий видит ровно ту строку, хеш которой смог предъявить, то есть токен которой у него уже есть. Новых ролей и обхода RLS не нужно.
- Отвергнут вариант с функцией `SECURITY DEFINER`: она обходит политики целиком, а при `FORCE` RLS её владельцем пришлось бы делать отдельную привилегированную роль. Отверстие шире, и ошибка в теле функции открывает всю таблицу. Причина записана в самой миграции, чтобы решение не пересматривали вслепую.
- **Найдено на первом прогоне:** PostgreSQL применяет к `SELECT ... FOR UPDATE` ещё и политики изменения. Блокирующий запрос под контекстом одного лишь хеша возвращал пустой результат, и вход был невозможен. Ротация разделена на два шага: поиск владельца по хешу без блокировки, затем блокировка уже под контекстом пользователя. Сериализация одновременных обновлений сохранена — блокировка берётся до любых изменений.
- `npm run test:integration` — PASS, 88 проверок; 12 из них в `tests/integration/sessions.test.ts` и идут **через роль времени выполнения**: под владельцем таблиц политика по хешу не понадобилась бы и проверка прошла бы вхолостую.
- Проверено: запрет по умолчанию без контекста, пустой результат по неверному хешу, хранение хеша вместо токена, ротация, отклонение неизвестного и истёкшего токена, отзыв семьи при повторном использовании вместе с действующим токеном владельца, непричастность других семей и других пользователей, невозможность отозвать чужую семью, гонка двух обновлений.
- Прототип `services/backend/spikes/session-rotation/` удалён: production-модуль его повторяет, а две расходящиеся копии одного механизма — прямо то, чего требует избегать план. Найденные на прототипе ошибки остаются в `docs/security-prototype-session-rotation.md`.

### Проверки входа и закрытого доступа (P1-02, частично)

- Доступ закрыт по умолчанию: проверка access-токена вешается на приложение целиком, публичные пути перечислены в `PUBLIC_PATHS` (`src/shared/auth/require-auth.ts`). Забытый маршрут перестаёт работать вместо того, чтобы остаться открытым.
- Access-токен непрозрачный, живёт 15 минут, хранится хешем в той же строке сессии. Проверяется по базе, поэтому отзыв действует немедленно; подписанный токен пришлось бы считать действительным до истечения срока либо вести отдельный список отозванных.
- Ротация гасит прежний access вместе с refresh: иначе после обновления сессии старый токен отвечал бы ещё пятнадцать минут.
- Вход по синтетической личности разрешён только при `DEV_AUTH_ENABLED` вне production; при `NODE_ENV=production` с этим флагом конфигурация отказывается загружаться. При выключенном флаге маршрут отвечает 404, а не 403.
- Идентификатор синтетического пользователя выводится из subject детерминированно: искать существующего по subject нельзя, политика изоляции показывает только собственную строку, а для этого идентификатор уже нужен.
- **Живая проверка нашла утечку.** Необработанная ошибка возвращала клиенту текст ошибки PostgreSQL с именем колонки — разведка схемы без усилий. Добавлен обработчик с ответом `internal_error`; проверка на утечку добавлена в набор.
- Та же живая проверка поймала мою же ошибку в команде: миграции были запущены под ролью приложения, у которой нет прав менять схему, а вывод я отправил в `/dev/null`. Миграции выполняет владелец, приложение работает ролью без `BYPASSRLS` — две разные строки подключения, обе печатает `scripts/dev_db.sh`.
- `npm run test:integration` — PASS, 106 проверок в одиннадцати файлах; 18 из них — вход и доступ. Живьём через curl: 401 без токена, вход, `/me` с токеном, обновление, отказ прежнего access после обновления, `token_reuse_detected` при повторном предъявлении refresh.

## Особое внимание

1. Snapshot/ledger ≠ raw client state; awards только server engine.
2. `rescheduled` — ось расписания; не блокирует completion.
3. Same root activity: timer/self-report/device evidence не умножают награду.
4. User sequence под транзакционным lock; cursor не перескакивает через недополученные batches.
5. Mastery сохраняется; игровые последствия Protection заморожены.
6. Условия уровня 100 проверены математически, коэффициенты ещё не откалиброваны реальным пилотом.
7. Точный model ID/библиотека WebRTC/hosting provider пока не выбраны и не проверены; для них есть конкретные задачи, это не скрытые готовые зависимости.
