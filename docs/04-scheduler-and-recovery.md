# 04. Scheduler, календарь и Recovery Engine

## 1. Граница между интеллектом и алгоритмом

Goal Planner предлагает содержание, частоту, ожидаемую длительность и dependencies. Scheduler размещает задачи по детерминированным правилам. Recovery решает судьбу невыполненных commitments и формирует ограниченные новые варианты. LLM не имеет права объявить план допустимым, если математические ограничения нарушены.

В MVP: ручное планирование, пересчёт по запросу и предложение плана следующего дня. Самостоятельное изменение расписания по поведенческим паттернам — Phase 6, после включения пользователем automation policy.

## 2. Семантика времени

| Значение | Хранение | Пример |
|---|---|---|
| Instant | UTC timestamp + исходная zone | Звонок 25 сентября 17:30 Europe/Moscow |
| Floating wall time | local time + recurrence zone policy | Каждый будний день в 08:00 местного времени |
| Date-only | local date; end exclusive | Deadline «до 25 сентября» без установленного часа |
| Duration | elapsed seconds | 45 реальных минут, не разница строк wall time |
| User-day | локальная дата + конкретные начала/концы UTC | День 15 сентября при boundary 04:00 заканчивается 16 сентября 04:00 |

`userDayAt(t)`: перевести instant в effective user timezone; выбрать последнюю календарную границу day_boundary не позже t. Строить следующую границу через календарную дату, не `t + 86400`. Интервалы везде полуоткрытые `[start,end)`.

DST policy v0.1: несуществующее локальное время сдвигается к первому допустимому instant после разрыва; при повторяющемся времени выбирать раннее вхождение для начала, и первое вхождение конца строго после начала. UI предупреждает об автоматически скорректированном точном событии до принятия. All-day event занимает локальные календарные даты, не искусственные 24 часа.

Timezone change: absolute встречи сохраняют instant; floating routines перестраиваются с будущей границы; вчерашние `user_days/credit_day` неизменяемы. Зафиксировать effective policy change; не создавать второй день наград при перелёте. Rolling 24h XP cap действует независимо от зон. Day Boundary меняется с ближайшего ещё не открытого user-day, не пересчитывая закрытую историю. Неточная команда «завтра после работы» требует известного графика; при неизвестном — уточнение без записи.

## 3. Вход Scheduler

Immutable `PlanningSnapshot`:

- now, user timezone/boundary, horizon, calendar/profile/goal versions;
- фиксированные busy events, сон/дорога/отдых, availability, quiet hours;
- task candidates: normal/minimum duration, earliest start, deadline, priority, dependencies, energy demand, preferred windows;
- уже active/completed tasks, вручную locked placements;
- недельный бюджет по каждой цели и total sustainable capacity;
- recovery budget, planned rest/protection, reason for recalculation;
- rule version и history summaries. История влияет на soft preference, не меняет fixed events.

Energy в MVP — self-report low/normal/high и выбранные пользователем окна. Не выводить физическое состояние из HealthKit без согласия и не считать отсутствие данных низкой энергией.

## 4. Ограничения

**Hard:** нет пересечений, задача целиком помещается в free interval, не нарушаются hard dependencies и hard deadline, сон/защищённый отдых/locked events не двигаются, recovery cap, max daily budget, начатая задача не переносится без явной команды.

**Soft:** предпочтительное время, энергия, main quest, приоритет, минимум переключений, справедливый прогресс целей, сохранение ранее принятого плана.

`free_minutes = union(availability) − union(fixed_busy + protected_rest + travel_buffers)`.

`planned_budget = min(user_daily_limit, floor(free_minutes × 0.70))` как initial default. Остальные 30% — резерв жизни, не запас для принудительного Recovery. Пользователь может изменить коэффициент. Предлагаемые интервалы обрезаются по реальным свободным окнам, а не только общей сумме минут.

Default: 5-минутная сетка размещения, 5-минутный буфер между cognitively different activities, максимум 3 priority goals в одном дне. Значения конфигурируемы и не медицинские нормы.

## 5. Алгоритм MVP

1. Получить согласованный snapshot и version vector; expand recurrence на 14 user-days.
2. Исключить completed/cancelled/excused, future blocked dependencies; active/locked сохранить.
3. Рассчитать free intervals и дневные/недельные budgets.
4. Проверить dependency DAG. При цикле вернуть `dependency_cycle`, не пытаться угадать порядок.
5. Отсортировать кандидатов: hard deadline urgency → priority (`critical > high > normal > low > optional`) → main quest → dependency order → стабильный ID.
6. Для кандидата найти feasible slots normal; оценить soft score: preference + energy fit + goal deficit − movement cost − fragmentation. Равенство: более ранний слот, затем ID.
7. Если normal не помещается — проверить minimum. Minimum не создаётся автоматически для задач, где меньший объём бессмысленен.
8. Если minimum не помещается — предложить перенос в горизонт; optional может остаться unscheduled.
9. Повторно проверить весь план, суммарные бюджеты, интервалы и deadlines.
10. Вернуть **PlanProposal** с diff, reason codes и непоместившимися задачами. При hard конфликте `partially_feasible`/`infeasible`, а не фиктивный «успех».

Greedy algorithm не гарантирует математически лучший план. Для личной версии он прост и объясним. Solver/constraint optimization вводить в Phase 6, только если fixtures показывают, что эвристика регулярно упускает допустимое расписание.

## 6. PlanProposal и принятие

Поля: `proposal_id, scope, base_plan_version, input_versions, created_at, expires_at, placements_added, placements_changed, tasks_unscheduled, variant_changes, total_minutes_before/after, violations, reason_codes`.

UI показывает конкретные изменения: «Английский 20 → 5 минут; тренировка → завтра; главное задание сохранено». Награды пересчитываются по engine, не текстом LLM.

`accept_plan(proposal_id, expected_base_version)` повторно валидирует **актуальные** busy events, consent/automation policy и deadlines под транзакцией. Если во время диалога добавилась встреча, вернуть `proposal_stale`, пересчитать и показать новый diff. Нельзя принять старый план поверх ручных изменений.

Default approval policy:

- Явное «перенеси эту тренировку на завтра в 18:00» при однозначной задаче и допустимом слоте — одна команда с Undo.
- Неоднозначное время/несколько тренировок — уточнение.
- Создание цели/roadmap, массовая перестройка, рост нагрузки — proposal + одно принятие.
- Пользователь может разрешить будущие автоматические перестановки в заданных пределах; policy версионируется, её отзыв отменяет ещё не выполненные предложения.

## 7. Пример нехватки времени

Исходно: работа до 18:00, свободно 18:30–22:00; тренировка 60, английский 20, проект 45. Работа затянулась до 20:00, доступно 20:20–22:00, защищённый сон позже 22:30.

Main project → 20:20–21:05; буфер 5; английский minimum → 21:10–21:15; тренировка → следующий допустимый день. Даже если осталось 45 минут календарного окна, нельзя автоматически считать его безопасным для тренировки без учёта установленного дневного лимита/энергии. Вывод содержит причины и доступные альтернативы.

## 8. Deadline и конец дня

- `deadline_kind=hard`: после due_at задача становится overdue; система сообщает о сроке, но сохраняет возможность записать фактическое позднее выполнение с `late=true`.
- `deadline_kind=soft`: предложение переноса, а не автоматический failure.
- `assigned_user_day` определяет обычный close/missed, а deadline — своевременность. Это разные измерения.
- Server day-close идемпотентен; клиент может предварительно вывести «срок прошёл», пока сеть недоступна.
- Late offline completion с фактическим временем до boundary корректирует missed, streak, review и отменяет неиспользованный Recovery.
- Активный timer на границе дня не крутится бесконечно: запрашивается подтверждение elapsed и продолжения, учитываются только фактические slices.

## 9. Recovery: факты, причина, варианты

Состояния case: `awaiting_reason → excused | assessed → proposal_pending → scheduled → resolved | expired | cancelled`.

| Причина пользователя | Действие по умолчанию | Debt |
|---|---|---:|
| Болезнь, травма, чрезвычайное событие, семейные обстоятельства | Excused, уменьшение плана, предложить Protection | 0 |
| План не помещался / непредвиденная работа | Исправить capacity, перепланировать, не компенсировать автоматически | 0 |
| Усталость | Minimum/rest; оценка нагрузки по self-report | 0 |
| Забыл / сознательно отложил | Предложить маленький возврат, reminder/time adjustment | +1 после подтверждения |
| Нет ответа / неизвестно | Сохранить missed, предложить ответ позже | 0 |

AI может классифицировать ответ и попросить короткое уточнение, но не решать, что пользователь «на самом деле не болел». Режим Commander меняет тон, не политику.

### Лимиты v0.1

- Recovery Debt — счётчик незакрытых небольших возвратов, максимум 3; не деньги и не отрицательный Lifetime XP.
- Формула: `Debt = sum(debt_units)` для неистёкших/неразрешённых assessed cases; каждый case имеет 0 или 1 unit. Если уже 3, новый пропуск создаёт diagnostic без четвёртого скрытого debt. Разрешение/истечение case обнуляет его unit через событие; числовая проекция принадлежит rule engine.
- За один missed создаётся максимум один case и одна recovery replacement.
- Не более 1 дополнительного recovery quest/day.
- Дополнительная нагрузка `min(15% × normal_planned_minutes, 20 minutes, remaining_feasible_capacity)`; при base=0 дополнительной нагрузки нет.
- Максимальный возраст unresolved debt — 7 user-days; затем expires и запускается Plan Diagnostic, если проблема повторяется. Не суммировать старый долг месяцами.
- Recovery имеет смысловую связь с целью: возвращение к 5–10 минутам нужной практики, не случайное наказание.
- Recovery Quest не создаёт новый debt при пропуске. Награда обычная по activity, без bonus за накопление долгов.

Пример: обычный план 60 минут → максимум 9 добавочных минут. Recovery minimum 15 минут не помещается: заменить часть необязательного плана или предложить 5 минут осмысленного действия; не округлять лимит вверх до 15.

## 10. Decision tree восстановления

1. Исходная задача уже не нужна? Cancel/archive remaining, debt resolved.
2. Повторяющаяся привычка имеет новую occurrence завтра? Не переносить вчерашнюю целиком; рассмотреть ближайшую обычную практику как возврат.
3. Есть deadline и зависимый milestone? Предложить перенос/компромисс с последствиями; невозможность явно показать.
4. Minimum сохраняет смысл и помещается в cap? Предложить его.
5. Эквивалентное действие возможно? Создать replacement с linked metric, не произвольную «штрафную тренировку».
6. Нет capacity? Отменить компенсационную нагрузку и уменьшить план. Уважение ограничений важнее погашения игрового счётчика.

После фактического late completion: если recovery не начат — cancel его и debt; если уже выполнен — сохранить реальное второе действие с обычными anti-grind caps, закрыть case без двойного штрафа.

## 11. Адаптация и диагностика

Window 7 eligible дней, минимум 5 commitments: completion по объёму <60% либо ≥3 переносов одной family → diagnostic suggestion. Не делать статистических выводов из двух наблюдений.

Completion 80–90% — наблюдать; >90% две недели + low self-reported difficulty + согласие → увеличение **одного** параметра максимум на 10%: длительность, частота либо сложность. <60% → предложить уменьшить объём до 20% и сначала убрать optional. Это общие настройки планирования; спортивная нагрузка не масштабируется автоматически без отдельной предметной проверки.

Изменения только на будущие commitments. Исторический denominator фиксирован при принятии плана. Не делать выполнение вчера «100%», уменьшив сегодня старые normal durations.

## 12. Forecast и эксперименты — Phase 6

Forecast использует конкретную goal metric: оставшийся объём / фактический устойчивый темп за 4–8 недель, с диапазоном неопределённости. При <4 недель/малой выборке — «недостаточно данных». Для skill exam результат не выводится линейно из времени; прогнозировать этапы практики, а не обещать B1.

Состояния: on_track / ahead / behind / insufficient_data. Объяснение содержит sample window, assumptions, диапазон даты и последствия изменения нагрузки.

Эксперимент: согласованная гипотеза, одно изменение (например, утро вместо вечера), baseline/trial, заранее выбранная метрика, срок 7–14 дней. Отчёт описывает наблюдение у пользователя, не заявляет причинность или научную доказанность по одной неделе.
