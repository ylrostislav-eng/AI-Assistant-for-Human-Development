# Прототип изоляции арендаторов (часть P0-04)

Дата: 2026-09-15. Проверяемое утверждение [09. Безопасность](09-security-and-operations.md), раздел 2: изоляция пользователей держится на RLS, runtime-роли без `BYPASSRLS` и транзакционном контексте, который не протекает между соединениями пула.

Проверка выполнена до создания доменных таблиц намеренно: если механизм негоден, переделывать пришлось бы сразу все таблицы, а обнаружилось бы это на данных двух живых пользователей.

Код проверки — `services/backend/tests/integration/tenant-isolation.test.ts`. Это spike: таблица прототипа создаётся и удаляется самим тестом, production-модуля identity ещё нет (P1-02).

## Проверенный механизм

1. **Отдельная runtime-роль.** `LOGIN NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE`, без владения таблицами; права — только `SELECT/INSERT/UPDATE/DELETE`.
2. **RLS с `FORCE`.** `ENABLE ROW LEVEL SECURITY` недостаточно: владелец таблицы политики обходит, и ошибочный запуск приложения под владельцем снимает изоляцию молча. `FORCE ROW LEVEL SECURITY` распространяет политику и на владельца.
3. **Политика с `USING` и `WITH CHECK`.** `USING` закрывает чтение и изменение чужих строк, `WITH CHECK` запрещает записать строку от чужого имени. Одного `USING` недостаточно: без `WITH CHECK` вставка с чужим `user_id` проходит.
4. **Транзакционный контекст.** `set_config('app.user_id', $1, true)` — значение живёт до конца транзакции. Параметризация обязательна: `SET LOCAL` не принимает параметры, а склейка строки открыла бы SQL-инъекцию через значение из токена.
5. **`NULLIF` перед приведением к uuid.** Пустая строка в настройке иначе роняет запрос, и отсутствие контекста выглядело бы сбоем базы, а не отказом в доступе.

## Результаты

Среда: PostgreSQL 16.13, одноразовый локальный кластер. Команда: `DATABASE_URL=... npm run test:integration`.

| Проверка | Результат |
|---|---|
| Runtime-роль не superuser и не `BYPASSRLS` | PASS |
| Арендатор видит только свои строки | PASS |
| `UPDATE` чужой строки затрагивает 0 строк, данные целы | PASS |
| `DELETE` чужой строки затрагивает 0 строк, данные целы | PASS |
| `INSERT` от чужого имени отклонён политикой | PASS |
| Без контекста не видно ни одной строки (запрет по умолчанию) | PASS |
| Контекст не протекает в следующую транзакцию того же соединения | PASS |
| Два арендатора в одном пуле видят разные данные | PASS |

**Отрицательный контроль.** На копии таблицы без RLS под той же runtime-ролью и тем же контекстом арендатор видит обе строки вместо одной. Проверка отличает работающий механизм от неработающего, а не проходит вхолостую. Проверка роли на `rolsuper`/`rolbypassrls` стоит в файле первой по той же причине: под суперпользователем остальные проверки прошли бы при отключённой изоляции.

## Что это не доказывает

- Доменные таблицы. Изоляция появляется у каждой таблицы отдельно; забытые `ENABLE`/`FORCE`/политика не обнаруживаются сами. В P1-01 нужна проверка, которая перечисляет таблицы с пользовательскими данными без RLS и падает на найденной.
- Проверка identity token, ротация refresh, отзыв устройства — это P1-02; прототип берёт `user_id` как данность.
- Контекст в worker и административные операции с audit — отдельная работа, здесь не проверялись.
- Внешний пул соединений (pgbouncer в режиме transaction pooling) не проверялся; при его появлении транзакционный контекст нужно проверить заново.
- Аутентификация в проверке — `trust` локального кластера. Реальные учётные данные приходят из secret manager, см. раздел 3 документа 09.
- Поведение и стоимость RLS на больших объёмах не измерялись.
