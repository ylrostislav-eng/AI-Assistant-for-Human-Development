# 03. Progression Engine: полная спецификация v0.1

**Канонические коэффициенты:** [progression-v0.1.json](contracts/progression-v0.1.json). Формулы — в этом документе. Расчётные проверки — [check_architecture.py](validation/check_architecture.py). Это модель игрового баланса, не измеритель интеллекта, здоровья или профессиональной квалификации.

## 1. Ответственность и инварианты

Progression Engine — чистый детерминированный модуль. Вход: валидированные Activity/Evidence, frozen reward profile, предыдущие дневные buckets, RuleSet и явное расчётное время. Выход: allocations, ledger changes, уровни, форма, rank transitions и объяснение расчёта. Никакой сети, SQL, системного now(), случайности или вызова LLM внутри.

Сервис вокруг движка атомарно записывает результат. AI/клиент не присылают утверждённые XP, level, stat или rank. Модель может предложить difficulty/skill; policy валидирует и замораживает профиль награды.

Инварианты:

1. Все XP, уровни, значения stats, skill mastery и Current Form стартуют с 0; стартовый rank F.
2. Одна физическая активность учитывается один раз независимо от числа задач, устройств и подтверждений.
3. Global XP не увеличивается от количества привязанных навыков или характеристик.
4. Разбиение одной активности на 100 частей не увеличивает итоговую награду.
5. Повтор команды возвращает прежний результат. Undo создаёт компенсацию, не удаляет прошлые записи.
6. Обычный пропуск не уменьшает Lifetime XP/Mastery. Коррекция ошибки может уменьшить их, с объяснением.
7. Нагрузка, повторяемость, overlap, day/rolling caps ограничивают награду; долг не растёт от Recovery Quest.
8. Ни rank, ни Level 100 не означают превосходство человека или клиническую оценку.

## 2. Что означает XP

- `LifetimeXP`: учтённое развитие во всех направлениях после начала использования.
- `SkillMasteryXP`: часть тех же наград, направленная на конкретный навык.
- `StatXP`: часть тех же наград, направленная на широкие характеристики.
- `CurrentForm`: расчётный индикатор недавней практики, от 0 до 100%, отдельно от XP.

Global, skill и stat ledger — разные проекции одной награды. Их нельзя складывать в «общий XP». Baseline «уже знаю английский B1» не даёт заработанного XP; оно влияет на подбор заданий и хранится отдельно.

## 3. Длительность и идентичность активности

`eligible_duration = min(actual_active_duration, approved_normal_duration)`; ad-hoc обычное действие без заранее заданного плана получает максимум 120 минут credited duration. Лишнее время сохраняется в истории и не поощряет бесконечный рабочий день. Пользователь может заранее изменить будущий объём в пределах capacity.

Рабочие интервалы объединяются по `root_activity_id`; паузы исключаются. Одновременные интервалы разных root не умножают часы: пересечение относится к более ранней запланированной активности, затем tie-breaker root UUID. Пользователь может исправить распределение. Для self-report без точных start/end хранить неопределённый интервал внутри user-day; такие длительности складываются в общий временной бюджет, не представляются проверенными таймером. Минимальные unit-based routines рассматриваются отдельно.

Для одного дня accepted slices сортируются по `(occurred_start, root_activity_id, slice_index)`. Неизвестное точное время — после известных интервалов, stable tie-breaker root UUID. Этот порядок — часть v0.1. Позднее подтверждение может изменить распределение дневного лимита между активностями; UI показывает одну коррекцию итогов.

## 4. Базовая награда и diminishing returns

Базовая ставка: **0.5 XP за допустимую минуту**.

Для каждого временного сегмента применяются два коэффициента накопленной нагрузки:

| Положение минуты внутри того же activity family за user-day | `f_family` |
|---|---:|
| 0–60 минут | 1.00 |
| 60–120 | 0.50 |
| 120–180 | 0.25 |
| после 180 | 0.00 |

| Положение минуты внутри всех developmental activities за user-day | `f_global` |
|---|---:|
| 0–120 минут | 1.00 |
| 120–240 | 0.50 |
| после 240 | 0.00 |

`baseXP = Σ(segment_minutes × 0.5 × f_family × f_global)`.

Сегмент режется на пересечениях границ обоих buckets. Счётчики учитывают суммарные допустимые минуты, включая участок с нулевым XP, а не только оплаченные минуты. Все способы записи одной деятельности используют общий family. Смена названия, goal, skill или template не сбрасывает family/global buckets.

Это **не рекомендация заниматься 4 часа ежедневно**. Это верхняя граница игровых начислений, а планировщик использует индивидуальный бюджет, сон и восстановление.

### Коэффициенты задачи

`rawXP = baseXP × D × Q × E × C × N`.

| Коэффициент | Значения | Кто устанавливает |
|---|---|---|
| Difficulty D | E=0.50, D=0.75, C=1.00, B=1.20, A=1.40, S=1.60 | Policy по approved challenge stage и baseline |
| Quality Q | incomplete quality=0.70, standard=1.00, rubric result=1.05 | Результат заранее заданной rubric; по умолчанию 1.00 |
| Evidence E | self=1.00, timer=1.02, device/result/milestone=1.05 | Валидатор evidence; выбрать максимум, не перемножать |
| Consistency C | `1 + 0.02 × min(4, floor(success_days_14 / 3))` | По закрытым предыдущим 14 eligible дням |
| Novelty N | 1.00 в MVP | Позже только новая подтверждённая ступень rubric, максимум 1.05 |

Quality не дублирует partial fraction: 15 из 45 минут уже дают меньше через duration; второй штраф за длительность запрещён. Q=0.70 допустим только для отдельного известного критерия качества, не по настроению ИИ. Неоценённое качество — 1.00.

Привычная полезная практика не теряет XP от того, что повторяется неделями. Снижать относительную difficulty только когда выполненные этапы/результаты показывают, что задание стало лёгким, и только для будущих occurrences. В Phase 3 без надёжной rubric default C; повышающий коэффициент нельзя получить одной фразой «это S».

Детерминированная DifficultyPolicy: rubric задаёт упорядоченные challenge stages 0…5 и условия допуска, baseline фиксирует пройденную ступень 0…5. Для допущенной задачи `delta = task_stage − baseline_stage`: ≤−2 → E, −1 → D, 0 → C, 1 → B, 2 → A, ≥3 → S. Stage не произвольное число от модели: ссылка должна вести на существующую принятую rubric с выполненными prerequisites. Новая custom rubric до принятия/калибровки имеет D≤1.00 (C). AI предлагает описание/ступень, backend проверяет schema, references, prerequisites и cap; пользователь может снизить заявленную сложность. Изменение baseline/rubric после нескольких реальных результатов применяется только к будущим заданиям. Это воспроизводимое правило игровой оценки, а не объективное доказательство сложности.

### Routine

Простое автоматическое действие («выпить воду», «поставить галочку») — `kind=routine`: до **1 XP на family за день**, до **5 XP суммарно за день**, только за естественную завершённую occurrence. Никакой награды за повторный self-report того же действия. Routine не получает difficulty/consistency/evidence множители и не засчитывается как qualifying skill practice. Полезность таких привычек остаётся в журнале.

### Общие caps

- До **180 Global XP за user-day**, включая routine и milestone.
- Дополнительно до **180 XP в любом скользящем 24-часовом окне**, привязанном к фактическому credit instant; смена timezone/day boundary не удваивает лимит.
- Начислять только остаток лимита; skill/stat allocations берутся из реально выданного Global XP.
- Ни одному выполнению не гарантируется нижний XP-порог. Короткое meaningful action может дать долю XP, routine — ноль после лимита.

Rolling cap обрабатывается в каноническом порядке наград; award в момент `t` получает `min(raw, 180 - sum(awards in (t-24h,t)))`. Сегменты одной активности распределяются по их конечным instants; routine/milestone имеют один completion instant. Коррекция прошлой активности пересчитывает затронутые дни и downstream rolling-window effects до стабилизации. Для длинного backfill это job; snapshot остаётся `recalculating`, затем атомарно публикуется новая revision.

## 5. Округление и ledger

Длительности в секундах; коэффициенты — целые basis points, базовая ставка — рациональное число. Внутри использовать точную rational/decimal арифметику с достаточной точностью. Округлять **вниз до 1 milli-XP после суммирования root/day bucket**, а не каждый односекундный slice. Остаток bucket переносится при последующей дописи частей той же активности. Это предотвращает exploit/потери на дроблении.

Запись: `amount_mxp, rule_version, input_hash, activity_root, bucket_key, account_type, account_id, calculation_revision`. Для распределения процентов сначала floor каждой доли; остаток milli-XP раздать по убыванию дробных остатков с tie-breaker target ID. Сумма skill allocations (при наличии навыков) = Global award, stat allocations = Global award.

Награда подтверждается транзакцией с user lock. Replay считает желаемые awards и пишет **дельту к уже начисленному**, включая отрицательные compensations. Повтор replay той же input_hash/revision не создаёт новые entries.

## 6. Minimum, partial, completion и streak

Пример normal 45 мин, minimum 15:

- normal выполнен: `completed`, `variant=normal`, считаем фактическую допустимую длительность.
- minimum выполнен: `completed`, `variant=minimum`, 15 минут XP; minimum считается успешным для streak.
- сделано 8 минут: `partial`, 8 минут XP; minimum ещё не достигнут.
- minimum 15, затем ещё 30: одна root activity, новая суммарная награда; выдаётся только разница.

Не награждать отдельно actions/checklist, родительскую задачу и habit. Это один фактический объём.

`success_day`: выполнено хотя бы одно frozen meaningful commitment до minimum; routine не достаточна. Streak увеличивается только в eligible дни с запланированной развивающей работой. Запланированный отдых/excused/protection — neutral: не увеличивает и не ломает. Невыполненный eligible день обнуляет current streak после reconciliation. Lifetime best streak сохраняется. UI отдельно показывает completion normal/minimum, чтобы minimum не выглядел полным объёмом.

## 7. Уровни: медленная кривая

Порог Lifetime для целого уровня L≥0:

`T(L) = 20L + 8L² + 0.25L³ XP`.

Точная реализация: `T_mxp(L) = 20000L + 8000L² + 250L³`.

`LifetimeLevel(X) = max { L : T_mxp(L) ≤ X_mxp }` — integer binary search. Не пытаться вычислять inverse float polynomial. Уровень не ограничен 100, это символическая большая отметка.

`progress = (X - T(L)) / (T(L+1) - T(L))`.

Примерные сроки при постоянном уже выданном XP, без перерывов:

| Уровень | Накопленный XP | 30 XP/день | 70 XP/день | 120 XP/день |
|---:|---:|---:|---:|---:|
| 1 | 28.25 | 1 день | 1 день | 1 день |
| 5 | 331.25 | 12 дней | 5 дней | 3 дня |
| 10 | 1 250 | 42 дня | 18 дней | 11 дней |
| 20 | 5 600 | 187 дней | 80 дней | 47 дней |
| 40 | 29 600 | 987 дней | 423 дня | 247 дней |
| 60 | 84 000 | 2 800 дней | 1 200 дней | 700 дней |
| 100 | 332 000 | 11 067 дней | 4 743 дня | 2 767 дней |

При абсолютном cap 180 XP/day Level 100 требует минимум 1 845 наградных дней, примерно 5 лет непрерывного максимума. Это математическая нижняя граница; 120 XP/day не объявляется «здоровой нормой». Начальные 1–5 уровни быстрее, 20–40 — месяцы/годы. При 5 активных днях в неделю календарные сроки увеличиваются примерно в 1.4 раза.

## 8. Навыки, иерархия, Mastery

Порог Skill Level:

`S(L) = 30L + 12L² + 0.40L³ XP`.

`S_mxp(L) = 30000L + 12000L² + 400L³`; inverse — тот же integer binary search.

Прямые skill allocations делят фиксированный пул, максимум 3 skills. Если задача развивает Swift, родитель Programming показывает **агрегированную проекцию** прямого XP Programming + потомков. Родитель не получает вторую ledger-награду. Global XP по дереву не пересчитывается. При merge сохранять исходные ledger IDs и canonical skill mapping; суммировать уникальные allocations один раз.

Mastery в v1 не убывает со временем. Для получения отображаемых уровней 10/20/40/60/80/100 нужны соответственно 1/2/4/6/8/10 разных achieved checkpoints с заранее сохранённой rubric в этом skill subtree. Если XP достаточно, но gate не выполнен, уровень остаётся на 9/19/39/...; XP продолжает копиться, UI показывает «Доступна проверка навыка». Self-reported checkpoint допустим и честно подписан. Навык без теста может использовать демонстрацию результата/проект; не требовать экзамена или платного сервиса.

Это защищает от «100 раз нажал = мастер», но не доказывает реальные способности. Проверка `B1` и Skill Level не взаимозаменяемы.

Milestone award: 20 XP за валидированный новый результат, максимум 2 award за trailing 7 user-days, общий дневной/rolling cap сохраняется. Награда требует rubric, созданную до результата, и уникальный outcome fingerprint. Повтор/reimport/переименование не награждается. В MVP поддержать checkpoints и этот bounded award; стилизация Boss — Phase 6.

## 9. Характеристики

В MVP: BODY, ENDURANCE, MIND, FOCUS, DISCIPLINE, SOCIAL. RECOVERY — позднее после отдельной калибровки, чтобы не награждать длинный сон/«отдых» произвольными очками.

Доли stat profile сохраняются на occurrence. Например обучение: MIND 50%, FOCUS 30%, DISCIPLINE 20%; тренировка: BODY 50%, ENDURANCE 30%, DISCIPLINE 20%. DISCIPLINE положен для заранее принятого commitment; для незапланированной деятельности эта доля пропорционально распределяется между остальными stat. Шаблоны доступны пользователю для просмотра; список редактируется только по валидированным значениям.

`StatValue = floor(100 × 5 × log2(1 + StatXP / 100)) / 100`.

Это отображаемая нелинейная шкала, не проценты и не физические единицы. Точный stat XP хранится независимо от display. Для численной воспроизводимости server вычисляет canonical hundredths; Swift получает snapshot и допускается preview ±0.01. Log не используется для денежных/XP ledger вычислений.

`CurrentStatValue = StatValue × F_stat`, округление вниз до сотых. `F_stat` обновляется как форма соответствующих связанных практик; определения ниже. Нельзя скрыто вычитать StatXP за пропуск.

## 10. Current Form и decay

Период практики берётся из подтверждённого реалистичного плана и хранится как `MaintenanceTarget` на неделю. Он отражает время **поддержания текущей практики**, не желаемый недостижимый максимум. Target: ≥10 минут в неделю для active skill; точное значение индивидуально. Новый target применяется только с будущей user-week, с изменением версии.

Для каждого skill/stat и effective day d:

`r_d = min(1, qualifying_minutes_in_last_7_effective_days / weekly_maintenance_minutes)`.

`F_d = λ × F_(d-1) + (1 - λ) × r_d`, где `λ = 2^(-1 / H)`.

Начало F=0. H по умолчанию: физические skills 10 дней; учебные/social 21 день; stats 14 дней. Это настраиваемая игровая инерция, не медицинский half-life. Для parent skill суммировать уникальные минуты leaf/direct с ограничением overlap; наличие descendants не умножает r.

Qualifying minutes — реальные accepted developmental minutes, распределённые между skills по frozen allocations, независимо от срабатывания XP cap; не routine. Для формы использовать максимум индивидуального maintenance target, а не бесконечное время. При отсутствии практики сначала опустеет rolling-7 окно, затем при r=0 через H дней форма уменьшается вдвое. В отсутствие target archived skill использует последний target и естественный decay; архивирование не удаляет прошлый вес текущей недели.

### Режим защиты

Уважительная причина исключает день из adherence/streak denominator и не создаёт debt. При болезни/отпуске пользователь может включить **Protection**: frozen игровая форма, current level/rank и streak до 14 календарных дней; дальше предлагается продлить, продление разрешено. Effective clock формы не движется в protection, в его rolling window не добавляются нулевые дни. Квалифицированные действия журналируются; при добровольном выполнении reward рассчитывается обычно, но давление/напоминания о decay отключены.

Protection не утверждает, что реальная физическая форма сохранилась. Действия в Protection увеличивают Mastery/ledger, но не обновляют замороженные Form/rank inputs; обычный rolling-window расчёт продолжается с первого нового effective дня после защиты. После длительного перерыва — короткая повторная оценка baseline и более лёгкий старт. При продлении никакого автоматического «штрафа за болезнь».

## 11. Current Power и Current Level

На начало недели фиксируется focus set: active skills и stats с ненулевым mastery. Удаление/архивирование навыка не меняет denominator текущей недели. Новый навык с нулевым XP не обрушивает показатель. Вес каждого направления нормализуется из `sqrt(1 + mastered_XP)`; изменение focus set отражается в weekly snapshot.

- `F`: взвешенная форма skills; если skill XP отсутствует — форма stats.
- `A`: за 14 effective дней `min(1, actual_development_minutes / committed_development_minutes)`, denominator по frozen day commitments.
- `D`: доля выполненного commitment-объёма за 14 effective дней: для каждого `min(actual_amount/normal_amount,1)`, weighted by planned duration; excused/cancelled-before-commit excluded.
- `R`: число успешных eligible дней / число eligible дней за 14 effective дней.

Если для A/D/R нет eligible denominator — сохранять последнее рассчитанное значение соответствующей компоненты; если его никогда не было, использовать 1 как нейтральное исходное значение. Это не позволяет показателю внезапно вырасти при выпадении плохой недели из пустого окна. При отсутствии всей истории установить Power=0. При отсутствии активных skills использовать сохранённую форму заработанных stats, не присваивать всем 100%.

`Power = clamp(0.60F + 0.15A + 0.15D + 0.10R, 0, 1)`.

`CurrentLevel = floor(LifetimeLevel × (0.40 + 0.60Power))`.

При LifetimeLevel=0 CurrentLevel=0. При Power=1 уровни совпадают. При длительном отсутствии практики и frozen missed commitments показатели снижаются, но прошлое mastery остаётся. Даже если последние A/D/R были высокими, F→0 удерживает CurrentLevel ниже максимума. В UI пояснять, что Power — игровая оценка текущей практики; не писать «эффективность человека 86%».

## 12. Rank и защита от скачков

| Rank | Минимальный Lifetime Level | Минимальный Current Level | Power для входа | Earned active days lifetime | Разные checkpoints |
|---|---:|---:|---:|---:|---:|
| F | 0 | 0 | 0 | 0 | 0 |
| E | 5 | 4 | 0.45 | 5 | 0 |
| D | 10 | 8 | 0.50 | 20 | 1 |
| C | 20 | 16 | 0.55 | 60 | 3 |
| B | 35 | 28 | 0.60 | 150 | 5 |
| A | 50 | 40 | 0.65 | 300 | 8 |
| S | 70 | 56 | 0.70 | 600 | 12 |

Eligible rank = максимальный ряд, все условия которого выполнены. Earned active day — день с meaningful minimum, не routine/просто вход в приложение.

- Повышение: eligible rank удерживается 7 закрытых effective дней; entry в E тоже 7 дней. F задан изначально.
- Понижение: для текущего ранга Power ниже entry−0.10 **или** Current Level ниже entry−2 в течение 14 effective дней; снизить на одну ступень и перезапустить счётчик. Lifetime/achievement prerequisites не исчезают из-за отсутствия, но corrections могут пересчитать eligibility.
- Protection останавливает счётчики. Оповещение одно после подтверждённого перехода; без тревожного push каждый день.
- Исторический `highest_rank` сохраняется; Current Rank может уменьшаться.

## 13. Миграция баланса

RuleSet неизменяем после активации. Новый набор применяется к новым occurrences с `effective_at`. В личном пилоте разрешён явно обозначенный пересчёт всего баланса с backup и отчётом before/after; публично — только через отдельную миграцию продукта.

Не изменять прошлые awarded XP «за ночь». Formula levels при новой версии либо сохраняется для пользователя до season migration, либо переводится по явно описанному mapping; выбрать в ADR до публичного баланса. В MVP весь пользователь закреплён за одной версией.
